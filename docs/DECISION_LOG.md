## 架构两端 · 解析端导航

本项目是**两段式**：`解析端`（源 Excel → 标准 JSON）+ `查询页`（标准 JSON → 可视化）。本仓库（`fba-rate-query/`）只承载**查询页**与**最终 JSON 数据**；解析端在仓库外，位于 `~/Documents/trae_projects/fba-rate-parser/`。`拆解运价` 这类改动（把价格拆成构成项）主要落在**解析端**，续接时先分清要动哪一端。

解析端已沉淀的权威文档（只做导航，此处不复制内容）：

- `docs/报价表_读取协议_模板.md` — 标准字段字典、计费主体、派送方式/通道拆分、计费档、单位约定（元/KG vs 元/CBM）、附加费规则、多供应商适配规范。
- `docs/皓鹏运价表读取规则.md` — 英国空卡铁海的读取规则：Sheet 布局、列段含义、行段定义、查价步骤伪代码、防错校验。

## 待办 / 下一步

### 优先级高：拆解运价（下一阶段主线）
> 落点在**解析端**：改的是 `fba-rate-parser/` 的读取规则与生成产物，不在本仓库。先读上面的 `docs/报价表_读取协议_模板.md`、`docs/皓鹏运价表读取规则.md`，再看源表是否有附加费列。

现状的「价格」只是一个数字映射（如 `{"21KG+":40.5,...}`），没有拆成构成项。下一阶段的方向是把价格拆成结构化的组成，并做跨渠道比价。开工前提要先对齐一个语义输入，例如：

- 把单列价格拆为「基础运费 + 附加费」明细分列（燃油/旺季/偏远/分拨派送等）——需要源表里是否有这些附加费列，需先看源表
- 同一目的地 + 同一重量档，横向比价取最低渠道——依赖现有数据已具备（同目的地多渠道并存）

另有一处**数据与代码不一致**值得先处理：渲染逻辑里引用了 `r.城市`、`r.开始邮编`、`r.结束邮编`，但当前数据源实际上没有这三个字段（用的是 `交货地`/`交货仓库`/`FBA仓库`），目的地兜底目前落在 `FBA仓库`。继续扩展前应先统一，避免新数据进入后兜底失效。

### 优先级中：单一数据源
`index.html` 与 `fba-rate-query.html` 现在靠手工同步保持一致（用 `diff` 校验），漂移风险高。更稳的做法是让解析脚本输出唯一一份页面文件，`index.html` 作为构建产物由它生成，而不是手工维护两个手足文件。

- **气泡随滚动/缩放自动隐藏**：气泡用 `position:fixed`，锚点是单元格 `getBoundingClientRect()`，滚动后会脱离所指内容。方案是监听 `document` 的 `scroll`（捕获模式，兼捕竖向滚动与 `.tbl-scroll` 横向滚动）与 `window.resize`，滚动或缩放即收起。
- **推送代理「自动检测」而非「写死」**：一开始给 GitHub 配了常驻代理，Clash 开着顺畅，一旦关闭，无人监听的端口反而让超时更严重。改成运行时探测（`nc -z 127.0.0.1 7897`），开则走代理、关则直连，封装在 `/Users/Zhuanz1/git-push.sh`，对用户透明。
- **不做过度自动化**：用户提出过「自动启动 Clash 并选最优节点」，判断该需求依赖具体的 Clash 客户端与配置，无法安全全自动，未实现，改为上述检测脚本。

## 踩坑点

- **多文件同步**：三处结构一致的页面（`index.html`、`fba-rate-query.html`、`/tmp/fba_page_template.html`）必须逐字节一致。任何一处漏改都会造成线上「改了没生效」。每步提交前用 `diff fba-rate-query.html index.html` 校验。
- **推送超时**：直连 GitHub 时常 `Recv failure: Operation timed out`。用 `/Users/Zhuanz1/git-push.sh` 触发，或先确认 Clash 在 `127.0.0.1:7897` 监听。
- **计费单位易混**：`单位` 存的是 `KG` / `CBM`（不带「元/」）。按体积计费的 `CBM` 记录不能按 KG 直接查，否则比价会错。
- **两套筛选口径**：`运输方式` 是 `干线/末端` 拼接（如 `空运/快递派`），前端拆成两段独立筛选；`渠道名称` 是更完整的拼接，两者不等价。
